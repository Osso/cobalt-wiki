## Rerender fan-out fix, 2026-09-24

Not deployed; branch in the report. Cause (reproduced by `deepwell/tests/page_rerender_fanout.rs` on the old code): every `full` rerender, including sweep and dependent jobs, ran the outdater unconditionally and queued its includers, its whole category when it is a `_template`, and every page's navigation when it is a bar, each at depth+1. A `_template`'s category contains the template, so its job requeued the category at every depth; the inverted `rerender-skip` check runs fast loops and skips only pages last updated outside the window. A full sweep of the 14-page first fixture ran 216 jobs, up to depth 50; one nested include edit ran 35 jobs across depths 1–3. Views were not a producer: view-time rerenders are `standalone`.

Now ([rerender invalidation](../../specs/cobalt-rerender-invalidation.md)): the change queues every affected page once, including bar consumers of affected navigation pages; dependent jobs are `standalone` and queue nothing; pending jobs are deduplicated per page and type; a `full` rerender outdates only when its output changed under the same build. The final 16-page fixture: sweep 0 jobs, include edit 22 jobs (one per dependent plus one navigation rerender per page), none queued while draining.

After deploying: jobs already queued as `full` outdate only when their output changed under the current build, so the existing backlog drains without multiplying. Renderer changes need no sweep (pages rerender on view); a sweep, if run, queues nothing even as `full`.
