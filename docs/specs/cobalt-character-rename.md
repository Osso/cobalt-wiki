# Cobalt character rename

A character's short name is the page name in `character:<name>` or `bgc:<name>`. The site uses it as the character's tag, its `re:<name>` mention tag, a token in writing/arc/chain name lists, the `RelationshipBox` `pagename`, link targets, and the portrait file `icons/icon_<name>.jpg`. Renaming changes all of these together. The display name (page title, form `name`) does not change.

Decisions (user, 2026-10-15): anyone who can edit the character page may rename it; it runs as a background job with progress; there is no dedicated undo (rename back instead).

## What it must do

- [x] `character_rename_preview {page_id,new_name}` returns `{old_name,new_name,old_slug,new_slug,preview_token,icon,destination_tag_pages,count,pages}` for a live `character:`/`bgc:` page (not `_template`). The new name is trimmed and lowercased and must be lowercase letters, digits and single hyphens, different from the current name.
- [x] Preview and start require Page/Edit (and lock bypass) on the character page, on every affected page, and on `icons` when the icon is renamed. Denial on the character page is `PermissionDenied` 3106; on another page, `TagPageNotEditable` 4306.
- [x] An existing `character:<new>`/`bgc:<new>` is `PageSlugExists` 2104; an existing `icons/icon_<new>.jpg` is `FileExists` 2105. Existing destination tags are allowed only after explicit confirmation: preview reports `destination_tag_pages` (distinct live pages tagged `<new>` or `re:<new>`); the pane explains that existing tags stay and renamed references join them, and labels the confirmation accordingly. Start without `allow_existing_tags:true` when this count is nonzero fails `CharacterNameInUse` 4307, including direct RPC calls. Destination-only pages are not edited or added to edit-permission requirements; overlapping tags are deduplicated; name-list tokens and references follow the existing rename rules.
- [x] Affected pages are live pages whose change set is non-empty: tags `<old>`→`<new>` and `re:<old>`→`re:<new>`; writing/arc/chain `characters`/`references` whole tokens (same rule as [tag rename](cobalt-tag-admin.md)); `pagename=<old>` inside `RelationshipBox` includes (other includes' `pagename` stay); and `[[[character:<old>…]]]`/`[[[bgc:<old>…]]]` link targets. Prose, other words containing the name, and other fields stay unchanged.
- [x] `character_rename_start {page_id,new_name,preview_token,allow_existing_tags,ip_address}` (`allow_existing_tags` defaults to false) succeeds only if the recomputed preview token (page IDs/revisions, icon revision, the `_template` sources used for name lists, and destination-tag page IDs, not destination-only page revisions) matches (`TagPreviewStale` 4304 otherwise), records the operation, and queues the job; it returns `{operation_id}`.
- [x] The job re-checks the token under the site tag lock, then in one transaction moves the page to `<category>:<new>`, makes one ordinary revision per affected page (the character page gets its move revision plus one), and renames the icon file. Any failure rolls everything back and records the reason; nothing is retried. Rerender jobs caused by the edits are queued only after commit (each send retried up to 5 times with backoff) and dropped on rollback; whether a page's rerender is already pending is checked after commit, so a rerender that started during the rename is queued again. A failed commit or rollback is recorded as a failure like any other. Changes after confirmation make the job fail stale.
- [x] `character_rename_status {operation_id}` returns `{operation_id,status,done,total,error,new_slug}` to the renaming user only; `status` is `queued`, `running`, `done`, or `failed`. `total` counts the move, each page edit, and the icon rename.
- [x] The Rename character pane on character/bgc pages previews, confirms, shows progress, and opens the new page when done ([page actions](cobalt-page-actions.md)); `22c347754`, `framerail/tests/character-rename.test.ts` 8/8.
- Destination-tag confirmation in `e76275d9d..28a07a3e8` has no deployment proof yet. The production evidence below predates that change.
- [x] Production rename verified end to end, including the worker transaction and progress polling (2026-10-15, throwaway `bgc:zz-rename-probe` → `zz-rename-probe2` through the pane; a concurrent edit after start made operation 1 fail 4304 with nothing changed; proof `/tmp/cobalt-character-rename-live-proof.md`). ## How it works

- `deepwell/src/services/character_rename.rs`: planning (candidate pages: tag overlap or the name as a word in the source), preview token, job body `execute`, and `run_job`, which locks the queued row (`FOR UPDATE SKIP LOCKED`) in the transaction that runs `execute`, and records failure in a separate one.
- The job runs on the existing worker queue. It may outlast the queue's 30 s process time; a redelivered message that finds the row locked queues a check 30 s later, before the message is deleted, instead of finishing, so a job exists until the rename commits or fails. If the worker dies, its lock is released and the next check runs the rename from the start (progress resets to 0).
- Progress is a Redis counter (`character-rename:progress:<id>`, 24 h expiry), because uncommitted edits are invisible to status reads. The `character_rename` row holds the final outcome.
- Idle workers poll every `min-delay-poll-secs` doubling up to `max-delay-poll-secs`; the NixOS module sets the cap to 10 s (default 360 s, which made a live rename wait 23 s at 0/N), so a rename starts within about 10 s.
- The job holds the site tag lock for its whole run, so ordinary page edits and imports on the site wait until it finishes. At about 76 ms per real page, a character on 1,000 pages blocks edits for roughly 75 s.

## Known gaps (current cycle)

- `run_job` is covered only for the locked-row and finished-row claim outcomes; the commit/rollback path with deferred jobs is proven by one production run, not a test.
- A held rerender that still fails after 5 sends is dropped (logged); that page keeps its old rendering until its next change. Its pending marker is set once and removed when it is dropped, so the next change queues it; if Valkey also refuses that removal, the marker stays (logged) until its 1 h expiry.
- A failed rename's status shows the progress count of the rolled-back attempt.
- Rewriting name lists re-serializes the page's form data (e.g. `author: 'x'` becomes `author: x`); values are unchanged.
- `[[include CharacterList | tags=…]]` terms and absolute `https://…/character:<name>` URLs are not rewritten (4 and 2 occurrences site-wide for the five most-referenced characters).
